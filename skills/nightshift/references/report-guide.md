# Nightshift 조간 보고서 작성 가이드

조간보고나 스크럼에서 3분 안에 전달할 수 있는 보고서를 만든다. 성과는 분명하게 드러내되 과장하지 않고, 숫자와 원시 근거가 판단을 대신하게 한다.

## 작성 전 확인

1. `journal.jsonl`을 처음부터 끝까지 순서대로 재생한다.
2. 각 줄이 유효한 JSON인지 확인하고, 마지막 정상 이벤트 이후의 손상이나 누락을 별도로 표시한다.
3. `result`, `decision`, `mission_end` 이벤트를 보고서 사실의 주 근거로 사용한다.
4. 관련 `step`, 로그, 산출물은 근거 경로와 짧은 발췌에만 사용한다.
5. Git 상태, 파일 존재 여부, 커밋 SHA처럼 현재 확인할 수 있는 값은 보고서 생성 직전에 다시 확인한다.
6. 측정값과 추정값을 구분한다. 추정에는 추정 방법과 불확실성을 붙인다.
7. journal에 없는 성공, 원인, 인과관계, 절감 효과를 새로 만들지 않는다.

## 필수 구성과 순서

HTML, Markdown, PPT 모두 아래 순서를 유지한다.

1. 제목, run ID, 실행 기간, 전체 상태
2. Executive summary 5항목
3. 상태별 미션 수
4. 밤 작업 흐름
5. 미션별 결과 카드
6. 타임라인
7. 결정 필요
8. 다음 단계
9. journal 경로와 생성 시각

## Executive summary

정확히 5항목으로 작성하고, 항목마다 한 문장만 쓴다.

1. **한 일:** 밤에 수행한 범위와 가장 중요한 작업
2. **된 것:** 검증을 통과한 결과와 대표 수치
3. **막힌 것:** 실패·부분 완료·차단 상태와 직접 원인
4. **결정 필요:** 사용자가 선택하거나 승인해야 할 사항
5. **다음 단계:** 가치가 가장 큰 후속 작업

해당 내용이 없으면 항목을 없애지 말고 `없음`과 그 근거를 짧게 적는다. 미션 상태 수와 Executive summary의 표현이 서로 모순되지 않게 한다.

## 미션 카드

미션마다 같은 구조의 카드를 하나씩 만든다.

### 1. 목표

- handoff의 목표를 한 문장으로 옮긴다.
- 실행 중 범위가 바뀌었다면 원래 목표와 실제 범위를 나눠 쓴다.

### 2. 수행

- 핵심 행동을 시간순으로 2–5개만 적는다.
- 복구 시도는 결과에 영향을 준 것만 남기고 전체 내역은 journal 경로로 연결한다.
- 장기 작업은 launch, 주요 poll, 완료 감지, 수집 순서가 보이게 한다.

### 3. 증거

- 지표명, 값, 단위, 기대값, 허용오차, PASS 여부를 표로 표시한다.
- 각 수치에 전체 조건 라벨과 산출 명령을 붙인다.
- 로그 발췌는 미션당 10줄 이하로 제한하고 원본 로그 경로를 함께 적는다.
- 측정값은 `측정`, 계산으로 유도한 값은 `계산`, 불완전한 추정은 `추정`으로 표시한다.
- 프로세스의 `success` 출력만으로 성공을 주장하지 않는다.

### 4. 산출물

- 파일마다 절대 경로 또는 보고서 기준으로 해석 가능한 경로를 적는다.
- 코드 변경은 저장소, 브랜치, 커밋 SHA, dirty 여부를 적는다.
- 산출물이 없으면 `없음`과 이유를 적는다.

### 5. 상태

다음 배지만 사용한다.

- `PASS`: 선언된 결정적 검사를 모두 통과함
- `FAIL`: 선언된 결정적 검사에서 실패함
- `PARTIAL`: 일부 결과는 있으나 판정 근거 또는 범위가 부족함
- `SKIPPED`: 우선순위, 마감, 가드레일에 따라 시작하지 않음
- `BLOCKED`: 복구를 소진한 뒤 사용자 액션이나 외부 상태 변화가 필요함

PASS나 FAIL 앞에는 반드시 대응하는 `result` 이벤트가 있어야 한다. 결정적 검사가 없는 미션은 PASS로 올리지 않는다.

## 조건 라벨

비교 수치에는 가능한 범위에서 다음 항목을 모두 붙인다.

- 데이터셋 또는 코호트
- 코드 revision 또는 커밋 SHA
- 설정 이름과 핵심 파라미터
- 하드웨어 또는 외부 서비스
- seed
- 표본 수
- 측정 프로토콜과 반복 횟수

조건이 다른 결과를 한 행, 평균, 대표 수치로 합치지 않는다. 직접 비교할 수 없으면 표를 분리하고 차이를 콜아웃으로 설명한다.

## 시각화 우선순위

구조와 흐름은 긴 문장보다 도형으로 먼저 설명한다.

- 시스템 구성, 데이터 이동, 작업 순서는 템플릿의 `.flow`, `.lane`, `.steps`, `.step`, `.arrow`을 사용한다.
- PASS/FAIL 판단과 복구 분기는 `.branch`, `.b-ok`, `.b-fail`을 사용한다.
- 비교할 숫자가 2개 이상이면 표를 우선한다.
- 추이와 여러 조건의 비교는 데이터 시각화 스킬이 있으면 적용하고, 없으면 축·단위·범례가 있는 인라인 SVG를 사용한다.
- 열거형 사실, 산출물, 다음 단계는 `.chip`으로 압축한다.
- 색만으로 상태를 구분하지 말고 상태 텍스트를 함께 표시한다.
- 데이터가 부족하면 장식용 차트를 만들지 않는다.

## 타임라인

`journal.jsonl`의 timestamp로 작성한다.

- 최소 항목: run 시작, 미션 시작·종료, 장기 작업 launch·완료, breaker, constraint, wrap-up, report 생성
- 로컬 시간대를 표시하고 이벤트 순서를 바꾸지 않는다.
- 긴 대기 구간은 poll을 모두 나열하지 말고 시작, 대표 진행률, 완료 또는 마지막 상태만 표시한다.
- heartbeat는 cadence drift, 상태 변화, 의사결정이 있는 경우만 타임라인에 넣고 반복 확인은 요약한다.
- 예상보다 긴 공백이나 machine sleep 의심 구간은 숨기지 않고 원인을 표시한다.

## 결정 필요

사용자가 아침에 바로 행동할 수 있는 문장으로 쓴다.

- 무엇을 결정하거나 실행해야 하는가
- 왜 지금 필요한가
- 선택지와 영향은 무엇인가
- 권장안이 있으면 어떤 근거로 권장하는가
- 언제까지 필요한가

결정할 것이 없으면 `현재 결정 필요 없음`이라고 쓰고, 후속 자동 작업과 구분한다.

## 문체

- 제목과 표제는 명사형, 설명 본문은 간결한 `-다`체를 기본으로 한다.
- 성과를 숨기지 말되 `혁신적`, `압도적`, `획기적` 같은 근거 없는 강조는 쓰지 않는다.
- `성공적으로 수행했다`보다 실제 명령, 수치, 변화량을 앞에 둔다.
- 같은 사실을 요약, 카드, 다음 단계에서 장황하게 반복하지 않는다.
- 내부 프롬프트, 도구 선택 과정, 독자에게 필요 없는 작업 경위는 쓰지 않는다.
- 자연스러운 한국어 작성 스킬이 있으면 적용하고, 제공되는 검사기로 `report` 장르 검사를 실행한 뒤 문맥을 보고 수정한다.

## HTML 템플릿 채우기

1. `report-template.html`을 최종 경로에 복사한다.
2. 파일 상단 주석의 placeholder map만 먼저 읽는다.
3. 모든 삽입 문자열을 HTML escape한다. 템플릿이 허용한 반복 블록 외에는 임의의 HTML을 journal 값에서 직접 삽입하지 않는다.
4. `MISSION_CARD_START`와 `MISSION_CARD_END` 사이 블록을 미션 수만큼 복제한다.
5. `TIMELINE_ROW_START`와 `TIMELINE_ROW_END` 사이 블록을 선택한 타임라인 이벤트 수만큼 복제한다.
6. 흐름 단계가 더 필요하면 주석 속 완성 샘플을 참고해 `.step`과 `.arrow`을 복제한다.
7. 결정과 다음 단계는 안전하게 escape한 목록 항목으로 만든다.
8. placeholder map과 복제용 샘플 주석을 최종 보고서에서 제거한다.
9. 필수 placeholder가 남지 않았는지 검색한다.

## Markdown과 PPT 변형

Markdown은 필수 구성 순서를 유지하고, CSS 도형 대신 Mermaid를 가정하지 않는 ASCII 흐름 또는 표를 사용한다. 모든 근거 경로와 조건 라벨을 보존한다.

PPT는 다음 6장 구성을 기본으로 한다.

1. 제목과 Executive summary
2. 밤 작업 흐름
3. PASS 미션과 대표 수치
4. FAIL·PARTIAL·BLOCKED 미션과 복구
5. 결정 필요
6. 다음 단계와 산출물

PPT 생성 스킬이 없으면 슬라이드별 Markdown 아웃라인을 만들고, 실제 PPT 파일을 만들지 못했다는 사실을 보고한다.

## 좋은 카드와 나쁜 카드

좋은 예:

> **M1 · 지연 시간 검증 · PASS**
>
> 목표: C1 조건에서 p95 지연 시간 120 ms 이하 확인
>
> 결과: 114 ms, n=1,000, 허용오차 0 ms, C1=dataset-v3 / a1b2c3d / cfg-prod / A100 / seed 7 / protocol-v2
>
> 판정 명령: `python evaluate.py --config cfg-prod`
>
> 근거: `logs/m1-evaluate.log`, `artifacts/m1-metrics.json`

나쁜 예:

> 성능을 성공적으로 개선했고 대부분 정상으로 보인다. 일부 문제가 있었지만 전반적으로 좋은 결과다.

나쁜 예에는 수치, 조건, 판정 기준, 원시 근거, 상태의 의미가 없다. 표현을 다듬는 대신 근거부터 보강한다.

## 납품 전 검사

- Executive summary가 정확히 5항목인가
- 미션 수와 상태별 합계가 일치하는가
- 모든 PASS/FAIL에 선행 `result`가 있는가
- 모든 대표 수치에 조건, 단위, 기대값, 허용오차, 근거가 있는가
- 로그 발췌가 미션당 10줄 이하이며 원본 경로가 있는가
- 서로 다른 프로토콜을 같은 표나 헤드라인에 합치지 않았는가
- 결정 필요 문장이 사용자 행동으로 이어지는가
- HTML에 JavaScript, 외부 폰트, 외부 이미지, 원격 stylesheet 요청이 없는가
- 내부 앵커를 제외한 외부 `href`와 모든 `src`가 없는가
- 필수 placeholder와 복제용 주석이 남지 않았는가
- `report`와 단일 `run_end`을 기록하기 전에 모든 정리·검증을 끝냈으며, `run_end` 뒤에 파일이나 journal을 다시 수정하지 않았는가
- 화면 폭 1200px, 좁은 화면, 브라우저 인쇄 미리보기에서 읽을 수 있는가
- 보고서와 journal에 비밀값이 없고 안전한 변수명·경로만 남았는가
- 최종 보고서 목적지(handoff 지정 위치 또는 기본 CWD)와 run directory의 사본이 같은가
