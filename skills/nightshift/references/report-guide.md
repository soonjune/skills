# Nightshift 산출물 작성 가이드

밤이 끝나면 성격이 다른 두 문서를 만든다. 이 구분이 이 가이드의 핵심이다.

| 문서 | 목적 | 형식 | 위치 |
| --- | --- | --- | --- |
| **보고서** | 조간보고·스크럼에서 발표하는 기술 내용 보고 — 독자는 "이 주제가 지금 어떤 상태인가"를 얻는다 | HTML 기본 (요청 시 Markdown/PPT) | handoff가 지정한 목적지, 기본은 세션 시작 CWD |
| **야간 작업 로그** | "밤사이 무슨 일이 있었나"의 운영 기록 — 미션 진행, 시도와 복구, 시간 흐름, 결정 | Markdown, 요청 없이 자동 생성 | `<run-dir>/night-log-<run-id>.md` |

보고서는 동료 엔지니어가 그 주제에 대해 쓴 기술 보고서처럼 읽혀야 한다. 밤의 절차는 보고서의 주제가 아니다.

## 보고서 본문에서 분리할 것

다음은 **Nightshift의 제어 절차를 설명하는 맥락일 때만** 야간 로그로 보내고, 보고서에서는 재현과 출처 절의 경로 참조로만 남긴다. 단어 자체를 금지하지 않는다. 작업 대상이 서비스 heartbeat, polling 알고리즘, application journal, training run, mission scheduler라면 해당 용어는 기술 내용이므로 본문에서 그대로 쓴다.

- Nightshift 운영 의미의 run, run ID, 미션/M1, intake, wrap-up, heartbeat, poll, breaker, journal, handoff, write fence
- 밤 실행 절차의 서술이나 도식 ("handoff를 읽고 → 검증하고 → 실행했다")
- **타임라인·시간순 이벤트 목록** — 보고서에 타임라인 섹션을 만들지 않는다
- 미션 상태 집계 (PASS n개 / FAIL n개) — 판정 배지는 결과 주제별로만 사용
- 에이전트의 내부 판단 경위, 도구 선택, 프롬프트

나쁜 목차의 실례 (이렇게 나오면 실패): `01. Executive summary / 02. 밤 작업 흐름 / 03. 미션별 결과 / 04. 타임라인 / ...`

좋은 목차의 실례: `결과를 한 문장으로 / 조건 구분 / 방법 / 실험별 결과 / 결론과 적용안 / 재현·출처`

## 작성 전 확인

1. `journal.jsonl`을 처음부터 끝까지 순서대로 재생한다.
2. 각 줄이 유효한 JSON인지 확인하고, 마지막 정상 이벤트 이후의 손상이나 누락을 별도로 표시한다.
3. 사실 판정(성공·실패·수치)은 `result`, `decision`, `mission_end` 이벤트와 연결된 원시 근거에서만 가져온다.
4. 기간·경과 같은 메타데이터는 그 밖의 이벤트에서 가져오되, 보고서 본문이 아니라 야간 로그와 재현과 출처 절에 쓴다.
5. Git 상태, 파일 존재 여부, 커밋 SHA처럼 현재 확인할 수 있는 값은 생성 직전에 다시 확인한다.
6. 측정값과 추정값을 구분한다. 추정에는 추정 방법과 불확실성을 붙인다.
7. journal에 없는 성공, 원인, 인과관계, 절감 효과를 새로 만들지 않는다.

## 전개 방식 선택 (두괄식 vs 미괄식)

같은 필수 요소를 쓰되, 어떤 순서로 전개할지 내용을 보고 판단한다.

- **두괄식 (기본)**: 결론·효과부터 제시 — 결과 요약 → 배경과 방법 → 결과 → 결론과 적용안. 핵심 수치가 명확하고 임팩트가 클 때, 통과·개선처럼 헤드라인이 그 자체로 서는 밤에 쓴다.
- **미괄식**: 원인/목표 → 본론 → 결과/효과 — 배경과 목적(무엇을 위해, 왜) → 방법 → 결과 → 결론과 효과. 서사가 중요할 때 쓴다: 탐색·조사 작업, 부정적이거나 미묘한 결과, 전제를 이해해야 수치가 의미를 갖는 작업, 문제 정의 자체가 성과인 밤.
- 판단 기준: 첫 화면의 결과 한 문장이 맥락 없이도 설득력이 있는가. 있으면 두괄식, 맥락 없이는 오해되거나 밋밋하면 미괄식.
- 미괄식에서는 첫 섹션을 `배경과 목적`으로 제목을 바꿔 앞세우고, 결과 요약은 결론과 적용안 직전이나 그 자리에 합친다. 어느 쪽이든 섹션 번호와 nav를 실제 순서대로 다시 매긴다.

## 보고서 구성 요소 (HTML·Markdown·PPT 공통)

두괄식 기준 순서. 미괄식이면 위 규칙대로 재배열한다.

1. 제목 — 작업 주제 (run이 아니라 일)
2. 결과 요약 — 결과를 한 문장으로 + 핵심 수치 표 + 시사점 3–5개
3. 배경과 방법 — 무엇을 위해, 왜 이 작업인지와 방법·조건 (조건 표 필수)
4. 결과 — 주제(실험·검증 항목·산출물)별 섹션
5. 결론과 적용안
6. 결정 필요 — 없으면 섹션 삭제
7. 다음 단계
8. 재현과 출처 — 판정 명령, 산출물·로그·야간 로그·journal 경로

내용이 없는 선택 섹션은 채우지 말고 삭제하고 나머지 번호를 당긴다.

## 결과 근거가 없는 경우

`result` 이벤트가 하나도 없는 실행도 유효한 보고서를 남겨야 한다. 모든 항목이 시작 전에 건너뛰어졌거나 결정적 검사 전에 차단된 경우가 여기에 해당한다.

- 수치, 조건, 판정, 상태 배지를 `없음`, `N/A`, 0 같은 값으로 채우거나 만들어내지 않는다.
- 전체 판정은 `결과 없음`과 `status-neutral`을 사용하고, headline에는 작업 주제에 대해 어떤 기술 결론도 확정하지 못했다는 사실만 쓴다.
- HTML에서는 핵심 수치 표와 `#results` 섹션 및 nav 링크를 제거한다. 실제로 적용한 조건이 없으면 조건 표도 제거하고, 계획만 설명할 때는 계획임을 명시한다.
- 배경, 확인된 현재 상태, 결론을 내릴 수 없는 범위, 결정 필요, 다음 단계, 재현과 출처는 근거가 있는 만큼 유지한다. Nightshift 절차상의 상세 원인은 야간 로그에 두고 재현과 출처에서 그 경로를 연결한다.
- 재현 명령이나 산출물이 없으면 재현과 출처의 빈 명령·목록 컨테이너도 삭제한다. 야간 로그와 journal 경로는 항상 남긴다.
- `provenance_intro`와 `footer_evidence_note`는 결과 없음에 맞게 바꾼다. 존재하지 않는 본문 수치나 재현 명령이 있다고 쓰지 않는다.
- 일부 주제에는 `result`가 있고 다른 `PARTIAL`·`BLOCKED` 주제에는 수치가 없으면, 수치 없는 결과 카드에서 지표 표와 판정 명령 블록만 삭제한다. 요약, 실제 근거, 산출물, 빠진 증거는 남긴다.

## 결과 섹션 (주제별)

미션을 그대로 옮기지 말고 **주제로 번역한다**. "M1 완료"가 아니라 "스트리밍 경로 p95 지연 시간 검증"처럼 그 일 자체를 제목으로 쓴다.

- kicker: 실험·항목 ID (예: `E1 · 분리도 AUC`)
- 요약 문단: 무엇을 확인했고 그것이 무슨 의미인지 1–3문장
- 지표 표: 지표명, 값, 단위, 기대값, 허용오차, 판정, **전체 조건**
- 판정 명령과 근거 경로, 로그 발췌는 항목당 10줄 이하 + 원본 경로
- 산출물 경로
- 상태 배지: `PASS`(선언된 결정적 검사 통과) / `FAIL`(검사 실패) / `PARTIAL`(근거·범위 부족) / `BLOCKED`(외부 조치 필요). 시작하지 못한 항목은 보고서에서 결과로 다루지 말고 야간 로그와 "다음 단계"에만 남긴다.

PASS나 FAIL 앞에는 반드시 대응하는 `result` 이벤트가 있어야 한다. 결정적 검사가 없는 항목은 PASS로 올리지 않는다.

## 조건 라벨

비교 수치에는 가능한 범위에서 데이터셋·코드 revision·설정·하드웨어/서비스·seed·표본 수·프로토콜을 모두 붙인다. 조건이 다른 결과를 한 행, 평균, 대표 수치로 합치지 않는다. 직접 비교할 수 없으면 표를 분리하고 차이를 콜아웃으로 설명한다.

## 시각화

- 도형(`.flow`, `.lane`, `.steps`, `.step`, `.arrow`, `.branch`)은 **작업 대상**을 그린다: 대상 시스템 구조, 데이터 흐름, 실험 설계, 판정 기준 분기. **에이전트의 밤 절차를 도식화하지 않는다.**
- 비교할 숫자가 2개 이상이면 표를 우선한다.
- 추이와 여러 조건의 비교는 데이터 시각화 스킬이 있으면 적용하고, 없으면 축·단위·범례가 있는 인라인 SVG를 사용한다.
- 열거형 사실, 산출물, 다음 단계는 `.chip`으로 압축한다.
- 색만으로 상태를 구분하지 말고 상태 텍스트를 함께 표시한다. 데이터가 부족하면 장식용 차트를 만들지 않는다.

## 문체

- 제목과 표제는 명사형, 설명 본문은 간결한 `-다`체를 기본으로 한다.
- 성과를 숨기지 말되 `혁신적`, `압도적` 같은 근거 없는 강조는 쓰지 않는다. `성공적으로 수행했다`보다 실제 명령, 수치, 변화량을 앞에 둔다.
- 같은 사실을 요약, 결과, 다음 단계에서 장황하게 반복하지 않는다.
- 자연스러운 한국어 작성 스킬이 있으면 적용하고, 제공되는 검사기로 `report` 장르 검사를 실행한 뒤 문맥을 보고 수정한다.

## HTML 템플릿 채우기

1. `report-template.html`을 최종 경로에 복사한다.
2. 파일 상단 주석의 placeholder map만 먼저 읽는다.
3. 모든 삽입 문자열을 HTML escape한다. 템플릿이 허용한 반복 블록 외에는 임의의 HTML을 journal 값에서 직접 삽입하지 않는다.
4. 반복 블록 복제: `KEY_METRIC_ROW`(핵심 수치), `CONDITION_ROW`(조건 표), `RESULT_SECTION`(주제별 결과, 내부에 `METRIC_ROW`).
5. 대상 시스템 도형이 필요하면 `FLOW_SAMPLE` 주석을 참고해 02에 그린다.
6. 내용 없는 선택 섹션(결정 필요, 도형 등)은 nav 링크와 함께 삭제하고 번호를 당긴다.
7. placeholder map과 모든 샘플 주석을 최종 보고서에서 제거하고, 필수 placeholder가 남지 않았는지 검색한다.

## 야간 작업 로그 (Markdown, 자동 생성)

사용자가 요청하지 않아도 wrap-up에서 항상 `<run-dir>/night-log-<run-id>.md`로 생성한다. 여기가 "밤사이 무슨 일이 있었나"의 자리다.

구성:

1. `# 야간 작업 기록 — <제목> (<run-id>)` — 기간, 전체 상태, 미션 수와 상태별 집계
2. `## 미션별 기록` — 미션마다: 목표, 상태, 핵심 결과와 근거 경로, 시도·복구 내역(가설 사다리 진행, breaker), 남긴 산출물
3. `## 결정 기록` — `decision` 이벤트: 질문, 선택, 근거, 되돌림 가능 여부
4. `## 시간 흐름` — 주요 이벤트의 시간순 목록 (launch·완료·breaker·constraint·wrap-up). 반복 폴링은 요약하고, 예상보다 긴 공백은 원인을 표시
5. `## 제약과 이상 징후` — rate limit, quota, 클록 점프, drift
6. `## 산출물 목록` — 경로 전체

원천은 journal이며, 보고서와 동일한 비밀값 제거 규칙을 적용한다. 문장은 짧은 개조식으로 충분하다.

## Markdown과 PPT 변형 (보고서)

Markdown 보고서는 보고서 구성 순서를 그대로 유지하고, 도형 대신 표 또는 ASCII 다이어그램을 쓴다. 모든 근거 경로와 조건 라벨을 보존한다.

PPT는 다음 6장 구성을 기본으로 한다: ① 제목 + 결과 한 문장 + 핵심 수치 ② 배경과 방법(조건) ③–④ 주제별 결과 ⑤ 결론과 적용안 + 결정 필요 ⑥ 다음 단계. 전개 방식 선택은 PPT에도 동일하게 적용한다 — 미괄식이면 ②를 ① 앞에 두고 결과 요약을 ⑤ 쪽으로 옮긴다. PPT 생성 스킬이 없으면 슬라이드별 Markdown 아웃라인을 만들고, 실제 PPT 파일을 만들지 못했다는 사실을 보고한다.

## 좋은 예와 나쁜 예

좋은 예 (주제 중심):

> **E1 · 지연 시간 · PASS**
>

## 납품 전 검사

- 보고서 본문(재현과 출처 제외)에 Nightshift 제어 절차와 시간순 운영 서술이 없는가. 같은 단어가 작업 대상의 기술 용어라면 허용하고 문맥으로 구분했는가
- 전개 방식(두괄식/미괄식)이 내용에 맞게 선택됐고, 섹션 번호와 nav가 실제 순서와 일치하는가
- 제목과 각 결과 섹션이 작업 주제를 말하는가 (미션 번호가 아니라)
- 결과가 있으면 결과 한 문장과 핵심 수치에 조건·기준·판정이 붙어 있는가. `result`가 0개면 zero-result 변형을 적용하고 수치·결과 블록을 제거했는가
- 모든 PASS/FAIL에 선행 `result`가 있고, 서로 다른 조건을 한 표에 합치지 않았는가
- 로그 발췌가 항목당 10줄 이하이며 원본 경로가 있는가
- 결정 필요 문장이 사용자 행동으로 이어지는가
- HTML에 JavaScript, 외부 폰트·이미지·stylesheet 요청이 없고, 내부 앵커 외 `href`·모든 `src`가 없는가
- 필수 placeholder와 샘플 주석이 남지 않았고, 빈 선택 섹션을 삭제했는가
- 야간 로그가 run 디렉터리에 생성됐고, 보고서의 재현과 출처 절에서 그 경로를 가리키는가
- 보고서와 야간 로그에 비밀값이 없고 안전한 변수명·경로만 남았는가
- 최종 보고서 목적지(handoff 지정 위치 또는 기본 CWD)와 run 디렉터리 사본이 같은가
- 화면 폭 1200px, 좁은 화면, 브라우저 인쇄 미리보기에서 읽을 수 있는가
